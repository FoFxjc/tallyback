Tallyback

Delegate work. Know what came back.

Local, Git-native accountability for delegated agent work. Tallyback keeps a durable account of what was assigned, what an executor claims happened, what the repository can prove, and whether the result is ready to land — as a plain directory on your own machine, no server required.

The problem

An agent saying "done" is a claim, not a fact.

Delegated agent work follows a familiar shape — and loses its own history along the way.

User / PMdiscusses a goal
→
Delegates workto an agent, subagent, or human
→
Worktree / branchthe executor works in isolation
→
"Done"a claim arrives back
→
?what actually happened?

The missing layer has to answer:

  • What was promised?
  • What actually ran?
  • What came back?
  • What evidence supports it?
  • What has been verified?
  • What can safely integrate?
Activity is not completion. A claim is not evidence.

Core workflow

Declare → Dispatch → Observe → Verify → Settle

Five record boundaries, not a mandatory linear state machine — a Task can have several Attempts, and a Blocker or Claim can arrive at any point.

DeclareWhat is the task, and what would count as done?
→
DispatchWhich attempt, executor, worktree, and branch own it?
→
ObserveWhat claims, evidence, and blockers came back?
→
VerifyDo repository reality and Git support the claim?
→
SettleAccept, retry, abandon, or land?

The accountability model

Task = durable responsibility. Agent = replaceable executor.

A Task can survive several Attempts, across several agents, models, and worktrees, without losing continuity.

Topic └── Task the stable unit of responsibility ├── Declaration + Criteria what would count as done ├── Attempt one execution of the task │ ├── Executor a replaceable agent, subagent, process, or human │ └── Workspace / Branch the worktree an attempt owns ├── Claim a statement about progress or completion ├── Evidence a pointer to tests, commits, artifacts, observations ├── Verdict an independent per-criterion assessment └── Settlement the explicit accept / retry / abandon / land decision

Trust model

The ledger records judgments. It does not become truth by storing them.

Repository / Tests
↓
Git Facts
↓
Tallyback Records
↓
Model Memory

Agent-provided content is treated as untrusted data. Completion is never inferred solely from activity. Claims stay separate from Evidence and from Verdicts. Consequential claims are reconciled against repository/Git reality before they carry weight.

What it can do today

Implemented and exercised by 440+ tests, not aspirational.

Declare

Explicit objectives and named acceptance criteria before work starts.

Track Attempts

Executor, session, branch, and workspace ownership per Attempt.

Observe

Claims, evidence, blockers, and attempt outcomes — kept separate from each other.

Verify

Independent per-criterion Verdicts with confidence, rationale, and limitations.

Settle

Explicit accept / retry / abandon / land decisions — immutable and attributed.

View

A compact, ledger-derived per-task or project report. No live Git required.

Watch

Detects an Attempt whose workspace vanished, or a Claim with no branch advance.

Land

Read-only Git integration readiness, ordering, and file-overlap conflict awareness.

Bridge

A host-neutral adapter, plus one Claude Code plugin, driving the same CLI.

Parallel work → Land

Two branches, one integration-readiness report.

Task A ── dispatched to worktree A (branch feature/a) Task B ── dispatched to worktree B (branch feature/b) │ both return Claims + Evidence │ PM verifies each Claim (tallyback verdict) │ land authorization (settle --decision land) │ tallyback land: both git_ready, but flags an overlapping-file conflict between A and B │ a human/agent resolves order and performs the ordinary Git merge — outside Tallyback

Tallyback never orchestrates the workers and never performs the merge. A candidate's observed lifecycle moves conceptually through git_ready → (target moves) → git_behind → git_integrated once Git actually proves it landed — Land reports each state as observed, not as a guaranteed universal transition.

View vs. Land

Ledger reality and Git reality are different questions.

VIEW

Ledger reality.

  • What has been declared / claimed / verified / settled?
  • Pure projection over the ledger — no live Git.
  • Every Task is surfaceable, regardless of Settlement.

LAND

Git reality.

  • What is currently actionable for integration, right now?
  • Cross-checks ready_to_land against live Git state.
  • Read-only and advisory — never merges, rebases, or pushes.

And within Settlement, accept and land are two different decisions: accept judges a result acceptable; land is explicit authorization to integrate. Only an effective land Settlement enters ready_to_land. Verdict != acceptance != landing authorization != actual Git integration.

Boundaries

What Tallyback deliberately does not do

  • It does not choose or run your agents.
  • It does not orchestrate execution or schedule work.
  • It does not merge, rebase, or push Git branches.
  • It does not replace tests, CI, or code review.
  • It does not turn a model's claim into a fact merely by recording it.
  • It does not require a cloud account or database server.
